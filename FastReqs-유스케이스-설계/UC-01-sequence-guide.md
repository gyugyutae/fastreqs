# UC-01 요구사항 추가 — 시퀀스 다이어그램 작성 기준

## 목적과 범위
회의 대화에서 새 요구사항 후보를 찾아, 기존 요구사항과 충돌하지 않고 사용자가 승인한 경우 요구사항 문서에 추가한다.
중간발표 자료 8페이지의 유스케이스 1을 바탕으로 합의한 설계다. 발표 자료와 앱 코드는 변경하지 않는다. 발표 자료의 승인 후 충돌 검사 순서와 달리, 이번 설계는 충돌 검사 후 제안·승인한다.

## 사전 조건
- 사용자가 Slack에 로그인하고 봇이 채널에 참여한다.
- 채널과 PC의 요구사항 문서 폴더가 연결되어 있다.
- 봇 실행 프로그램과 분석 서비스에 접근할 수 있다.
- 요구사항 문서는 Slack 업로드 없이 연결 폴더에서 읽고 쓴다. Slack 파일 업로드는 회의록 입력이며 이번 대화 기반 흐름에서는 생략한다.

## 정상 시나리오
1. 사용자가 채널에서 회의 대화를 작성하고 시스템이 대화를 수집한다.
2. 사용자의 ‘분석해줘’ 요청 또는 종료 키워드 감지로 분석을 시작한다. 명시 요청은 현재 구현처럼 봇 멘션을 동반한다.
3. 직전 성공한 분석 이후 새 대화에서 추가할 요구사항 후보를 추출한다.
4. 연결된 요구사항 문서를 읽는다.
5. 후보와 기존 요구사항의 충돌 여부를 검사한다. 정상 흐름에서는 충돌이 없다.
6. 사용자에게 후보 내용과 반영 대상인 요구사항 문서를 제시한다.
7. 사용자가 해당 후보를 승인한다. 시스템은 후보 ID로 승인 대상을 식별한다.
8. 승인한 후보를 요구사항 문서에 추가하고 저장 성공을 확인한다.
9. 사용자에게 추가 완료를 알린다.

## 대안 흐름
- 5A 충돌 있음: 충돌 사실을 알리고 해당 후보의 추가를 종료한다. 문서는 변경하지 않는다. 충돌 해결은 별도 유스케이스다.
- 7A 거절: 문서를 변경하지 않고 종료한다.
- 7B 무응답: 승인 대기로 남으며 문서를 변경하지 않는다. 시간 제한은 정의하지 않는다.

## 표현 범위와 생략
- 하나의 후보를 처리하는 과정만 그린다. 요구사항 문서는 하나로 추상화한다.
- Who·What·Why 보완 질문, PRD·Spec·ADR 연쇄 변경, 회의록 업로드는 생략한다.
- 후보 없음, API/저장 실패, 여러 후보, 동시 승인, 외부 파일 편집은 이번 그림에서 생략한다.
- 실제 정책상 문서가 제안 이후 변경되면 재검사·재승인이 필요하지만 이번 그림에는 표시하지 않는다.
- 아래 객체와 메서드는 설계용 책임과 이름이며 실제 코드 클래스·함수와 일대일 대응하지 않는다.

## 참여 객체 — 왼쪽부터
| 표기 | 책임 |
|---|---|
| 사용자 (개발자·액터) | 회의 대화 입력, 분석 요청, 후보 승인·거절 |
| slackBot:SlackBot | Slack 이벤트 수신, 제안·결과 표시, 승인 전달 |
| controller:RequirementController | 대화 수집과 요구사항 추가 과정 조정 |
| analysisService:RequirementAnalysisService | 후보 추출과 의미 충돌 분석 |
| repository:RequirementDocumentRepository | 연결된 요구사항 문서 읽기·저장 |

## 객체 책임과 용어
- Controller: 유스케이스의 실행 순서와 승인 흐름을 조정한다.
- Service: 요구사항 후보 추출과 충돌 분석을 담당하며 내부적으로 외부 LLM을 이용한다. 이번 그림에서는 외부 LLM을 별도 라이프라인으로 펼치지 않는다.
- Repository: 로컬 요구사항 문서에 대한 읽기·저장 접근을 추상화한다. 데이터베이스에만 쓰는 용어는 아니다.
- SlackBot: Slack 이벤트와 사용자에게 보여줄 메시지를 연결하는 경계 객체다.
- 이 이름들은 설계상의 책임 분리다. 현재 코드의 클래스 구성을 그대로 묘사한 것은 아니다.

## 기억할 업무 순서
대화 → 분석 → 후보 추출 → 문서 조회 → 충돌 검사 → 제안 → 승인 → 저장 → 완료

객체 헤더는 objectName:ClassName 형식의 전공 용어를 사용하고, 호출 메시지는 한국어 동작명으로 작성한다. 호출은 동작이름(매개변수) 형태로 쓰고, 반환값은 결과 이름으로 쓴다. alt 등 UML 프레임 표기는 유지한다. 객체 헤더의 콜론 앞은 객체 이름, 뒤는 클래스 이름이다.

## 직접 그릴 메시지 순서
호출은 실선 화살표, 결과 반환은 점선 화살표로 그린다. 표의 인자는 개념적 데이터다.

| 순서  | 보내는 쪽 → 받는 쪽              | 메시지 이름 / 반환값           |
| --- | ------------------------- | ---------------------- |
| 1   | 사용자 → 슬랙 봇                | 대화전송(채널ID, 내용)         |
| 2   | 슬랙 봇 → 요구사항 컨트롤러          | 대화수집(채널ID, 내용)         |
| 3   | 슬랙 봇 → 요구사항 컨트롤러          | 분석시작(채널ID, 시작조건)       |
| 4   | 요구사항 컨트롤러 → 요구사항 분석 서비스   | 요구사항추출(새대화)            |
| 5   | 요구사항 분석 서비스 → 요구사항 컨트롤러   | 요구사항 후보(후보ID, 내용) [반환] |
| 6   | 요구사항 컨트롤러 → 요구사항 문서 리포지토리 | 기존요구사항조회(채널ID)         |
| 7   | 요구사항 문서 리포지토리 → 요구사항 컨트롤러 | 기존 요구사항 [반환]           |
| 8   | 요구사항 컨트롤러 → 요구사항 분석 서비스   | 충돌검사(후보, 기존요구사항)       |
| 9   | 요구사항 분석 서비스 → 요구사항 컨트롤러   | 충돌 결과 [반환]             |
| 10  | 요구사항 컨트롤러 → 슬랙 봇          | 추가제안(후보ID, 내용, 대상문서)   |
| 11  | 슬랙 봇 → 사용자                | 요구사항 추가 제안 표시          |
| 12  | 사용자 → 슬랙 봇                | 추가승인(후보ID)             |
| 13  | 슬랙 봇 → 요구사항 컨트롤러          | 승인처리(후보ID, 사용자ID)      |
| 14  | 요구사항 컨트롤러 → 요구사항 문서 리포지토리 | 요구사항추가(후보ID, 내용)       |
| 15  | 요구사항 문서 리포지토리 → 요구사항 컨트롤러 | 저장 성공 [반환]             |
| 16  | 요구사항 컨트롤러 → 슬랙 봇          | 추가완료알림(후보ID)           |
| 17  | 슬랙 봇 → 사용자                | 추가 완료 안내               |

3번 메시지는 분석 요청 또는 종료 키워드가 감지된 시점에 발생한다. 명시 요청을 그릴 때는 사용자 → 슬랙 봇의 분석요청(채널ID)를 3번 앞에 추가한다. 두 시작 경로를 모두 펼치지 말고 주석으로 대체해도 된다.

## 프레임과 활성막대
- 바깥 alt: [충돌 있음]은 알림 후 종료, [충돌 없음]에 제안 이후 흐름 배치.
- 충돌 없음 구역 안의 alt: [승인]에 저장·완료, [거절]에 변경 없이 종료. 무응답은 ‘승인 전 문서 변경 없음’ 주석으로 표시.
- loop/par는 이번 그림에 사용하지 않는다. 반복 수집은 메시지 1~2와 주석으로 간략화한다.
- 점선 세로선은 라이프라인이다. 실행 중인 구간만 좁은 직사각형 활성막대로 표시한다.
- 사용자 승인 대기 전체를 시스템 활성막대로 길게 채우지 않는다. 실행 구간을 분리한다.
- 객체 소멸은 없으므로 X를 표시하지 않는다. 객체 집합도 불필요하다.
- 메시지는 위에서 아래로 배치하고 같은 높이에 겹치지 않게 한다. 반환은 왼쪽으로 돌아가도 된다.

## draw.io 기초 파일 사용
1. diagrams.net 또는 draw.io에서 함께 제공한 .drawio 파일을 연다.
2. 객체 헤더와 라이프라인은 준비되어 있다. 첫 두 메시지는 예시다.
3. 위 메시지 표 순서대로 화살표와 활성막대를 추가한다. 활성막대 예시를 복제하고 실행 길이에 맞춘다.
4. 충돌 결과 뒤에 UML Combined Fragment를 추가하고 alt 조건을 적는다. 선택은 alt, 반복은 loop, 병렬은 par로 구분한다.
5. 공간이 부족하면 페이지 높이와 라이프라인을 늘린다. 겹치는 메시지는 세로 간격을 넓힌다.

기초 파일은 완성된 시퀀스 다이어그램이 아니다. 전체 메시지·분기는 직접 작성하도록 비워 두었다.
