## 2. 리팩토링한 파일 (양식의 파일 3칸)

### fastreqs/controller.py (← fastreqs/service.py)
1. **설계와 일관성**: `Service`를 설계 이름 `RequirementController`로 바꿨다. 시퀀스 메시지를 그대로 메서드로 만들었다(collectChat → `collect_chat`, startAnalysis → `start_analysis`, onApproved → `on_approved`, onRejected → `on_rejected`, onSelected → `on_selected`, checkAllConflicts → `check_all_conflicts`). 이전 이름은 `receive`/`analyze`/`decide`였다.
2. **큰 클래스(②)·단일 책임(SRP)**: 768줄 컨트롤러를 부품 3개로 나눴다. 대화 수집은 `chat_collector.ChatCollector`, 분석 실행은 `analysis_runner.AnalysisRunner`, 승인·저장·복구는 `approval_processor.ApprovalProcessor`가 맡는다. 컨트롤러는 설계 오퍼레이션을 받아 부품에 넘기기만 한다(150줄).
3. **긴 메서드(①)**: `receive` 복잡도 20 → `collect` 6, `analyze` 20 → `start` 5, `decide` 19 → `approve` 5. `__main__.main` 24 → 4.
4. **긴 파라미터 리스트(③)**: `process_approval(binding, id, version, approve, user)` 5개 + bool 플래그 → `on_approved(decision)` / `on_rejected(decision)`. `Decision` 데이터 클래스 하나로 묶었다. `_save_analysis` 6개 → `_save_round(round_, results)`(`AnalysisRound`). `create_candidate`의 thread/reserved_target → `CandidateOptions`.
5. **기본 타입 선호(⑤)**: 후보를 dict 대신 `records.CandidateRecord` 데이터 클래스로 다룬다. 상태 문자열 `'pending'` 등 → `CandidateStatus` 열거형.
6. **의존관계 역전(DIP)**: 컨트롤러는 `ports.py`의 `RequirementAnalyzer`·`RequirementView` 인터페이스만 안다. 구체 클래스는 `slack_bot.build_controller()`에서 조립한다.
7. **코딩 표준**: 한 줄 다중 문장 제거, 80자, 모든 메서드에 Args/Returns/Raises docstring, 한 글자 변수(`p`, `c`, `s`) → `record`, `candidate`, `source`, 매직 넘버 1_000_000 → `MAX_MEETING_FILE_BYTES`.

### fastreqs/analysis_service.py, fastreqs/llm_client.py (← fastreqs/analyzer.py)
1. **설계와 일관성**: «Model» `RequirementAnalysisService`의 두 오퍼레이션을 메서드로 만들었다. extractRequirements → `extract_requirements`, checkConflicts → `check_conflicts`. 이전에는 충돌 검사가 메서드로 없고 `service.make()` 안 if문 두 개에 숨어 있었다.
2. **충돌 검사는 한 곳에서**: 설계에서 두 곳에 있던 충돌 검사(`RequirementAnalysisService.충돌검사`, `ConflictDetector.detect`)를 `check_conflicts(documents, candidate=None)` 하나로 합쳤다. 후보가 있으면 후보와 기존 요구사항을(UC-01), 없으면 기존 요구사항끼리(UC-03) 비교한다. LLM이 돌려준 결과 중 문서에 실제로 있는 ID만 남긴다.
3. **단일 책임(SRP)**: HTTP 호출·재시도는 `llm_client.OpenRouterClient`(설계의 LlmClient)로, 프롬프트·검증은 분석 서비스로 나눴다. Why 근거 검사는 `_drop_ungrounded_why()`로 뺐다. 이전에는 `OpenRouter.analyze` 하나(복잡도 13)가 다 했다.
4. **리스코프 치환(LSP)**: 오프라인 데모의 `ScriptedAnalyzer`와 테스트용 가짜 분석기는 `RequirementAnalysisService`를 상속해 같은 시그니처로 바꿔 끼운다. 컨트롤러는 어느 것이 와도 똑같이 동작한다.
5. **코딩 표준**: 함수 안 import 4개 → 파일 맨 위. 중첩 함수 → `_make_strict()`. 재시도 상수(429/500…, 60초, 90초) → `RETRYABLE_STATUS` 등 이름 있는 상수. 이름이 모호하던 `conflicted` 필드 → `answers_contradict`(답변끼리 상충). 요구사항 충돌과 구분하기 위해서다.
6. **테스트**: 충돌 검사 7개, Why 근거 2개, 재시도·오류 5개.

### fastreqs/documents.py, fastreqs/document_repository.py (설계의 RequirementDocument, RequirementDocumentRepository)
1. **명명 규칙(동사+명사, snake_case)**: read → `read_documents`, sections → `parse_sections`, validate → `validate_documents`, plan → `build_patch`, preview → `render_diff`, digest → `compute_digest`, story_body → `render_story`. 파일명 문자열 `'prd.md'` 등 → `PRD`·`USER_STORIES`·`SPEC`·`ADR` 상수.
2. **Switch 문장(⑨)·개방 폐쇄(OCP)**: `plan()`의 `if kind=='story' … elif 'spec' … else` 35줄 분기 → `_plan_story`/`_plan_spec`/`_plan_adr` 함수와 `_PLANNERS` 딕셔너리. 새 문서 종류는 함수만 추가하고 `build_patch()`는 고치지 않는다.
3. **저장 경로를 하나로**: 설계의 `add(candidate)`(UC-01)와 `remove(requirement)`(UC-02, UC-03)를 Repository의 `save(channelId, change)` 하나로 합쳤다. 추가·수정·삭제·충돌 해소가 모두 같은 작업 저널과 롤백을 쓴다. 충돌 해소 패치는 `build_resolution_patch()`가 만든다.
4. **버그 수정**: 우선순위를 `row.replace('| 보통 |', …)` 문자열 치환으로 넣던 방식을 인자로 넘기도록 바꿨다. 제목에 '| 보통 |'이 들어가면 표가 깨지던 문제를 없앴다.
5. **테스트**: 섹션 파싱, 중복 ID 거부, 추가·수정·삭제 패치, 우선순위 유지, '|' 이스케이프, diff 출력 등 8개.

## 4. 설계 문서끼리 맞지 않던 곳과 처리

| # | 맞지 않던 곳 | 처리 |

| 1 | PRD는 "전체 충돌 평가"를 범위에서 뺐는데, 클래스 다이어그램에는 UC-03 충돌 확인이 있었다 | PRD 범위에 요구사항 충돌(UC-01 선택, UC-03 전체 확인)을 넣고 기능 FR-US-011, 결정 FR-ADR-006을 추가했다. 코드도 구현했다 |

| 7 | 구현 상태 설명이 달랐다(PRD·code-architecture는 "보류, 테스트 결과 없음", mvp-status는 "구현 완료, 테스트 25개") | 상태는 [mvp-status](../mvp-status.md) 한 곳에만 적고 다른 문서는 링크한다. 실제 수치(55개)로 고쳤다 |
| 8 | 모듈 이름 체계가 셋이었다(code-architecture의 slack_adapter 등, 클래스 다이어그램, 코드 파일) | code-architecture를 설계 클래스 = 코드 모듈 표로 다시 썼다 |

## 5. SOLID 점검

- **S**: 화면(SlackBot), 흐름 조정(Controller), 수집·분석·결정(부품 3개), 추출·충돌 판단(AnalysisService), HTTP(LlmClient), 저장(Repository)이 각자 한 가지 이유로만 바뀐다.
- **O**: 새 문서 종류는 `_plan_xxx` 함수만 추가한다. 새 화면(예: 다른 메신저)은 `RequirementView`를 구현하면 된다.
- **L**: 가짜 분석기들이 `RequirementAnalysisService`를 상속해 같은 시그니처로 바꿔 끼워진다.
- **I**: `ports.py`의 `LlmClient`, `RequirementAnalyzer`, `RequirementView`는 쓰는 쪽이 필요한 메서드만 가진다.
- **D**: 컨트롤러와 분석 서비스는 인터페이스에만 의존하고, 구체 클래스는 조립 루트(`build_controller`)에서 주입한다.

## 7. 코드 품질 장치 4가지: 구축 과정, 역할, 근거

### 7.1 구축 과정
| 단계 | 한 일 | 이유 |
|---|---|---|
| 1. 규칙 정리 | 리팩토링하며 정한 결정(설계 이름, 한 곳에서만 하는 일, 용어, 코딩 표준, 코드 스멜·SOLID)을 `CLAUDE.md`에 규칙으로 적음 | 다음 개발에서도 같은 기준을 쓰게 하려고 |
| 2. 기계 검사 | `tests/test_architecture.py`와 ruff 규칙 추가(인자 5개, 문장 50개). 일부러 규칙을 어기는 코드를 넣어 테스트가 실제로 실패하는지 확인 | 문서에 적은 규칙은 잊히기 쉬워서 |
| 3. CI | GitHub Actions로 main 푸시·PR마다(수동 실행 가능) Ubuntu Python 3.10·3.13, Windows Python 3.13에서 ruff·테스트·모의 데모 실행. 브랜치 보호 없이 main에 바로 올리고 결과를 확인하는 방식 | 팀원이 Claude 없이 고친 코드, 실제 실행 환경(Windows)까지 검사하려고 |
| 4. 설계 검토 에이전트 | `.claude/agents/design-reviewer.md`. 테스트로 판정할 수 없는 규칙과 설계·문서 일관성을 커밋 전에 검토(읽기 전용) | ④ 유사 데이터 그룹, ⑩ 중복 코드, O, I는 테스트로 잡을 수 없어서 |
| 5. 겹침 점검·병합 | 검토 에이전트에 CLAUDE.md 규칙이 그대로 복사돼 있던 부분을 지우고 CLAUDE.md를 가리키게 함(83줄 → 44줄). 테스트 개수를 문서와 맞추던 규칙과 테스트를 없앰. 빠져 있던 ⑧ 병렬 상속을 규칙표에 추가. UC-01 시퀀스 가이드를 design.md에 병합 | 같은 규칙을 두 곳에서 관리하면 다시 서로 어긋나므로 |

### 7.2 역할
| 장치 | 하는 일 | 코드 품질 말고 하는 일 | 비용 |
|---|---|---|---|
| CLAUDE.md | 규칙의 유일한 원본 | 푸시 계정 절차, 설계 기준 문서, 동작 원칙(승인 전 문서 변경 금지 등) | Claude가 세션마다 읽는 짧은 문서 |
| 테스트 + ruff | 기계적으로 판정되는 규칙 검사 | 기능 테스트는 승인·충돌·저장·복구 동작 검사 | 실행 1~3초 |
| CI | 같은 검사를 다른 환경·다른 사람의 커밋에서 실행. 규칙은 없음 | Windows·Python 3.10 실행 확인 | 공개 저장소라 무료, 푸시당 30~45초 |
| 설계 검토 에이전트 | 판단이 필요한 규칙, 문서 일관성 | 테스트가 없는 곳의 버그 발견 | 실행마다 토큰. 구조가 바뀌는 변경에만 사용 |

### 7.3 서로 다른 것을 잡았다는 근거 (이번 작업에서 실제로 있었던 일)
| 장치 | 잡은 것 | 다른 장치로는 |
|---|---|---|
| ruff | 처음 측정에서 표준 위반 510건. 인자 수 규칙을 켜자 생성자 2곳(인자 6개)을 잡아 `ControllerSettings`로 묶음 | 테스트·검토자는 줄 길이·인자 수를 세지 않음 |
| 아키텍처 테스트 | 컨트롤러에 `show_removed`를 넣거나 설계에 없는 오퍼레이션을 넣는 변경을 실패시킴(일부러 넣어 확인). ruff가 못 잡은 한 글자 변수 `as f`, `for b`를 잡음. 문서의 테스트 수가 실제와 달라진 것을 두 번 잡음 | ruff는 설계 문서와 코드를 대조하지 못함 |
| 설계 검토 에이전트 | **Windows 줄바꿈(CRLF)으로 저장된 문서를 읽으면 앱이 형식 오류로 멈추는 버그.** 맥에서 그때 있던 테스트 73개가 모두 통과한 상태에서 발견. 모든 파일을 CRLF로 바꿔 돌리면 테스트 45개가 실패하던 것을 수정 후 0개로 만듦. 그 밖에 테스트의 줄바꿈 문제, 하위 프로세스 인코딩, CI 캐시 키, 문서 문장 모순, 상태 문서의 과장 서술 | 테스트는 맥 환경에서만 돌아 통과했고, CI는 아직 없었음 |
| CI | 세 환경(Windows 포함)에서 통과를 실제로 확인한 유일한 장치. (CI 자체가 아니라 CI 도입 준비 과정에서 Windows 기본 인코딩에 한국어 파일이 깨질 곳 2개를 찾아 고침) | 로컬 검사는 맥 한 환경뿐 |

솔직한 한계: CI는 도입 후 아직 실패를 잡은 적이 없다. CI의 가치는 "Windows·Python 3.10에서도 통과한다"는 확인과, 팀원 커밋에 같은 검사를 거는 데 있다.

## 8. 남은 한계
- 충돌 판단은 LLM이 하므로 오탐이 있을 수 있다. 선택 전에는 문서를 바꾸지 않고, 실제 있는 ID만 허용해서 피해를 줄였다.
- 충돌 기능은 자동 테스트와 오프라인 모의 데모로만 확인했다. 실제 Slack·무료 모델 동작은 아직 확인하지 않았다([mvp-status](../mvp-status.md)).
- 기준 설계와 겹치는 이력 문서는 지웠고(git 기록에 남음), 남은 이력 자료(중간발표·품질 시나리오 pptx, UI 설계 pdf)는 고치지 않았다. 기준 설계는 design.md다.
