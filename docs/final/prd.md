# FastReqs PRD

상태: 합의된 중간발표 데모 설계. 앱 구현·Slack 연결·무료 모델 품질·Windows 실행은 미검증이며 구현 재개 요청 전까지 보류한다.

## 목적과 철학
Slack 대화/회의록에서 요구사항 변경을 발견하고, 사람이 보완·검토·승인한 부분만 로컬 문서에 반영한다. 자동화할 것은 정리와 영향 추적이며, 요구사항 확정 권한은 사용자에게 둔다. 누락된 목적을 AI가 추측하거나 승인 없이 문서를 바꾸면 안 된다.

유저스토리를 사용자 의도의 중심으로 삼는다. PRD는 제품 범위, Spec은 구현 계약, ADR은 기술 결정 이유를 담당한다. 같은 설명을 네 문서에 복제하지 않고 안정적 ID로 연결한다.

## 사용자·실행 환경
- 채널 참여자: 누구나 질문 답변·후보 정정·개별 승인/거절 가능. 한 사람의 발언도 후보 근거가 된다.
- 운영자: Windows 노트북에서 Python 앱 실행 및 터미널 최초 설정. 채널 링크/ID와 로컬 폴더를 연결한다.
- 실제 Slack 커스텀 앱, Bolt for Python/Slack SDK, Socket Mode. 실행 중인 노트북과 인터넷 연결이 필요하다.
- OpenRouter 무료 모델 사용. 앱 실행에 WSL/Docker/Codex는 필요하지 않다. 개발용 persuasion-review 하네스는 런타임과 별개다.

## 범위
채널 대화 수집·명시 요청/종료 키워드 분석, Markdown 회의록 스레드 분석, Who/What/Why 보완, 후보 정정, 추가/수정/삭제 개별 결정, Story/PRD 공동 반영, Spec/ADR 별도 결정, 미결 이월, 중복/재분석/수동 편집/저장 실패/재시작 보호를 포함한다.

제외: 음성/STT, 전체 충돌 평가와 /lint, Markdown 외 업로드, 임의 형식 문서, 긴 입력 자동 분할, 중단 중 대화 자동 수집, 유료 자동 전환, GUI.

## 관리하는 사용자 문서
| 파일 | 핵심 내용 | 변경 원칙 |
|---|---|---|
| user-stories.md | Who/What/Why·인수조건 | 변경의 중심, 안정적 US ID |
| prd.md | 제품 목적·범위·우선순위 | Story 승인과 관련 범위 공동 반영, 배경 보존 |
| spec.md | 동작·입출력·권한·예외·검증 | 실제 영향만 별도 승인 |
| adr.md | 배경·대안·결정·결과 | 실제 기술 결정만 별도 승인, 이력/대체 관계 보존 |

기준 자료는 사용자 소유 Markdown이다. DB에서 전체 문서를 재생성하지 않는다. 수동 편집을 허용하되 기본 템플릿/ID는 유지한다. 미승인 기술 영향은 ‘갱신 검토 필요’로 사용자에게 드러낸다.

## 성공 기준: 약 3분 데모
시연 대상은 FastReqs 자체가 아닌 가상 ‘팀 업무 검색 서비스’다. 초기 검색 US-001/다크 모드 US-002/관리자 CSV US-003 및 네 파일은 [샘플](../../demo-fixtures/team-search)에 있다.
1. 월간 보고서 .md 업로드 → 스레드 분석 → Why 질문 → 답변 → Story/PRD 전후 확인 → 승인 → 두 파일 변경.
2. 두 사람의 다크 모드 삭제 논의 → ‘수고하셨습니다’ → 후보 → 승인 → Story/PRD 삭제. Spec 제거는 별도 승인, 무관한 ADR은 유지.
3. 미승인·거절·오래된 버튼으로 문서가 바뀌지 않는다. 실패를 정상 완료로 표시하지 않는다.

무료 모델 작동/지연은 리허설에서 확인한다. 3분은 목표이며 검증된 성능이 아니다.
