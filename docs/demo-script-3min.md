# 3분 중간발표 데모 대본

상태: 설계/시연 계획. 실제 모델 지연/Windows/Slack 연결 미검증. 아래 시간은 목표 구간이다.
무료 모델 응답 시간이 길면 3분 내 완료를 보장할 수 없으며 구현 후 리허설로 조정한다.

## 사전 준비 (발표 시간 밖)
- 노트북 실행/최초 설정/Slack 봇 초대/채널 문서 폴더 연결 및 인증 점검 완료.
- 초기 네 문서를 매번 같은 상태로 준비. Story US-001 검색, US-002 다크모드, US-003 관리자 CSV. 월간 보고서는 초기 문서에 없음.
- Slack와 user-stories.md/prd.md 미리보기를 나란히 표시. 파일 자동 새로고침 동작은 리허설에서 확인.
- 개발자 A/B 역할의 Slack 사용자 두 명 또는 사용자 계정 두 개 준비. 두 사람 발언을 보이게 한다.
- 종료 키워드/파일 업로드/모델 호출을 사전 리허설하되 발표 채널에는 승인 대기 후보가 남지 않도록 준비.
- 업로드 파일: demo-fixtures/meeting-inputs/01-monthly-report.md.
- 해당 파일에는 Why 답변과 시연 지침을 넣지 않는다. 실제 보완 답변은 아래 대본에서만 가져온다.
- 토큰 값은 화면/문서에 표시하지 않는다.

## 0:00~0:15 소개
말: "FastReqs는 Slack 회의에서 요구사항 변경을 제안하고, 사람이 승인하면 로컬 문서를 갱신하는 봇입니다."
화면: 초기 User Stories의 다크모드 US-002와 PRD의 해당 범위를 짧게 보여준다. Spec/ADR은 탭 또는 파일 목록으로 존재를 표시하고 자세히 읽지 않는다.

## 0:15~1:25 월간 보고서 — 파일 입력/정보 보완/공동 반영
행동:
1. 월간 보고서 .md를 채널에 업로드.
2. 파일 메시지 스레드에 "@FastReqs 분석해줘" 입력.
3. Why 보완 질문에 "월간 실적 공유 시간을 줄이기 위해서입니다." 답변.
4. 완성된 Story와 관련 PRD 변경 미리보기를 보여주고 승인.
5. 로컬 Story/PRD에 월간보고서가 추가됨을 확인.
말: "목적이 빠져 있으면 추측하지 않고 질문합니다. 유저스토리와 PRD 변경을 함께 확인하고 승인합니다."
Spec/ADR 영향이 있는 경우 별도 검토 상태를 짧게 설명한다. 이 장면에서 모든 후속 카드를 승인하는 것을 필수로 두지 않는다.

## 1:25~2:40 다크 모드 — 두 사람 대화/종료 감지/삭제
A: "이번에는 검색과 보고서 기능에 집중하죠."
B: "그러면 다크 모드 US-002는 제품 범위에서 제외합시다."
A: "네, 다크 모드는 삭제하는 것으로 정하겠습니다."
B: "수고하셨습니다"
행동:
1. 별도 분석 멘션 없이 종료 인사로 분석 시작 확인.
2. US-002와 PRD 삭제 미리보기를 보여주고 승인.
3. Story/PRD 활성 범위에서 다크모드가 사라짐 확인.
4. 여유가 있으면 관련 Spec 제거 후보를 별도 승인. 시간이 없으면 검토 대기 상태를 표시하고 설명.
말: "종료 인사로 분석하지만, 승인 전에는 파일을 바꾸지 않습니다. 구현 계약인 Spec은 별도로 승인하고 ADR은 관련 기술 결정이 없으면 유지합니다."

## 2:40~3:00 마무리
말: "회의록과 대화 두 입력을 지원하고, 정보 보완과 개별 승인을 거쳐 문서를 반영합니다. 구현 명세와 기술 결정은 별도로 검토하며 변경 이력도 보존합니다."
화면: 최종 Story/PRD 및 기술 문서 검토 상태.

## 시간 조정
설정/설치, CSV 권한 변경, 후보 거절/정정/중복 클릭, 재시작, 오류 복구는 3분 핵심 시연에서 제외하고 질문 때 설명한다.
무료 모델 응답이 길면 응답 대기를 기능 설명에 활용하고 마지막 Spec 승인은 검토 대기 설명으로 축소한다.
미리 반영한 결과를 실시간 처리라고 소개하지 않는다. 실제 연결 실패 시 실패를 밝히고 준비한 화면/기록은 리허설 자료로 구분한다.
